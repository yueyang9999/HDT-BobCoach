# BobCoach 通用玩法内核：rollout 理解层与信号源纪律（阶段 1 计划）

日期：2026-08-31
目标：回答"怎样让算法真正理解游戏"——把评估信号从"观点级/闭环"提升到"机制事实级"，先用
确定性反事实 rollout 定位"算法不理解"的精确坐标，再在机制特征上建立通用价值内核，为跨赛季
卡牌/机制快速适应铺路。

## 一、问题诊断（基于迭代记录与生产代码）

### 1.1 三个结构性原因

1. **评估闭环不可信**：模拟器对手（HeuristicAI）与 Bob 都是自研启发式，A/B 本质是"启发式 A
   打赢启发式 B"。铁律 1 已 6 次验证"模拟器最优 ≠ 真实频率"；R403 前 4 次购买调优全部无净
   收益（弱对手环境下策略细节不敏感）。在此闭环内测出的"效果良好"不可作为正确性证据。
2. **学习对象错误**：R394–R444 共 20+ 次对手强化注入，仅 5 次有效（R408/R412/R417/R426/
   R425v2/R435/R439/R443），全部是"行为克隆"；"评分/偏好/时机注入"全部失败。单点规则没有
   组合深度，学不会"理解"——理解 = 能预测"这么做后面会发生什么" + 能判断"这个状态值多少"。
3. **记忆结构错误**：规则按赛季卡 ID 与 R 编号堆在代码里（换季失忆）；生产侧
   `UnifiedRankingPolicy` 为 diagnostic-only，模型 `EffectAcceptanceStatus` 未 accepted 时
   回退 legacy-v1.1.0；`BeamPlanner` 的"最优"= 最长可行动作链（无终局价值评估）；verifier
   LLM 判分是观点级信号，设计上不进验收门（criteria 文件已声明），但若曾以它判断"效果好"即被误导。

### 1.2 结论

> 算法"失忆且低智"的根因不是训练不够，而是**知识放错地方 + 评估信号不可信**。
> 修复方向不是继续堆规则，而是：让机制自己产出可信标签（rollout），把通用玩法学成
> 机制特征上的价值函数，把卡牌知识全部数据化。

## 二、核心论断

- **理解游戏 = 机制的预测模型 + 状态的价值模型**。预测模型来自可执行的机制引擎（模拟器，
  已有）；价值模型需要在机制特征上学习（要建）。
- **记忆 = 引擎（规则） + 版本化价值函数（通用玩法） + 数据化卡牌注册表（赛季知识）**。
  引擎和卡牌数据是"不会忘的记忆"；价值函数是"可迁移的理解"。
- **快速适应 = 通用内核 + 薄适配层**。新卡/新机制 = 注册表加数据 + 解释器认新标签 +
  几百局 rollout 微调适配器参数，不重训内核。

## 三、三层架构

```
层3 快速适应层（适配器）：升级曲线/流派偏好/英雄 playbook/饰品取舍 —— 少量参数，rollout 微调
层2 通用玩法内核（价值函数）：机制特征（经济/节奏/战力/血线/回合/引擎状态，非卡 ID）
层1 机制核心（引擎+数据）：确定性模拟器 = 规则记忆；cards.json + effect 标签 = 卡牌数据
```

- 层 1 已有（C# Simulator、Node 模拟器、cards.json、契约头），**保持**。
- 层 2 是本计划的主目标：rollout 标签训练机制特征价值函数；决策时用 1–3 层 rollout 搜索
  （候选枚举 + 硬约束过滤已有；`BeamPlanner` 的"最长路径"升级为"价值评估"）。
- 层 3 为后续阶段：适配器参数化 + 数据化卡牌 intake 流水线（`season_adapt_check.js` 雏形已有）。

## 四、信号源纪律（先于一切优化）

任何"测试效果良好"必须能回答：**结论来自哪级信号？**

| 信号级 | 来源 | 能否当验收 |
|---|---|---|
| 事实级 | 同 build + seed + 版本匹配的机制仿真结果（rollout 名次/胜率） | ✅ 唯一验收信号 |
| 观测级 | 真实回放（只对照节奏/行为，永不作为正确性标签） | ⚠️ 只对照 |
| 观点级 | LLM 判分 / verifier / 人工印象 | ❌ 只用于解释 |

- verifier MCP 降级为解释工具（写入本计划，禁止其结论进入任何验收/保留判定）。
- 回放标签继续遵守 AGENTS.md：玩家动作是观测事件，不是正确性标签。
- 阶段 0 落地：迭代记录模板增加"信号源"字段；`ITERATION_LEARNINGS.md` 中与卡 ID 无关的
  机制真相（升级费用表、伤害公式、三连/饰品路径、`模拟器最优≠真实频率`）沉淀为
  `mechanism-truths.json`（数据化，供通用内核输入）。

### 阶段 1 · 确定性反事实 rollout 原型（本次实现）

**目标**：在 Node 模拟器中实现候选动作的 rollout 价值估计器，并在经典决策点做离线对照，
输出"rollout 排序 vs 当前规则排序"分歧报告——即"算法不理解"的精确坐标。

**原理（确定性反事实）**：模拟器自 R146 起同 seed 可复现。以收集局同 seed 重放，回合 T 之前
Bob 行为与收集局完全一致 → 回合 T 状态逐位一致；此时**强制首决策 = 候选动作 A**，其余正常
执行 → 该 (seed, 状态, A) 得到一个确定性的终局名次。这就是"如果当时选了 A 会怎样"的可信答案，
无隐藏信息、无 LLM 意见、无版本错配。

**⚠️ 阶段 1 重大发现：模拟器卡表污染（2026-08-31 实证）**

实现过程中发现模拟器**同进程内同 seed 重放不确定**（A≠B≠C，独立进程却确定）：
- 根因：游戏内效果就地修改随从的 `mechanics` 等数组（如加嘲讽 TAUNT），而部分随从创建
  路径把 `card.mechanics` **按引用**赋给板面随从（PlayerAgent L700/715/896/957/996/1022
  等多处）→ `push` 直接污染 `cardsById` 卡表。
- 实证链：T4 同配对同种子同板面，run A 平局 vs run B 玩家7胜（护甲 9 vs 5）→ 差异字段
  `mechanics: A=["BACON_RALLY"] B=["BACON_RALLY","TAUNT"]` → 局后 `cardsById[BG33_886].
  mechanics` 永久含 TAUNT。
- 影响：**同进程批次的每个游戏都从被前局污染的卡表开始**——历史 A/B 批次（多局同进程）
  的结果可能被污染差异污染；R146 的"同 seed 可复现"修复只覆盖了 Math.random，不完整。
- 修复：`SimulationEngine.runOneGame` 每局开始前从首次快照恢复卡表（2026-08-31 已加，
  全调用方受益）；`rollout_probe.js` 另有同款兜底。修复后全状态 diff = 0 差异。
- 遗留：`cardsByTier` 等派生结构的引用级污染未全覆盖（低频路径）；后续 A/B 前建议增加
  "每局卡表指纹"断言（启动时记录，每局开始前校验一致）。

**组件**：

1. `SimulationEngine` 最小钩子（`this._rolloutProbe` 非空才生效，零行为影响）：
   - 收集钩子：Bob 决策循环第 0 轮、指定回合，回调 `(p, ctx, decisions)`（policy 全量排序）。
   - 强制钩子：Bob 决策循环第 0 轮、指定回合，将 `decisions` 替换为 `[候选动作]`。
   - 诊断钩子：`afterDecisions` / `afterCombat` / `pairs` / `combatResult`（--diag-full 用）。
2. `tools/simulation/rollout_probe.js`：
   - 收集模式：跑 K 局（seed S..S+K-1），在指定回合（默认 T4/T5/T7/T10 等经典决策点）
     记录状态快照 + policy 排序（按 `priority*confidence` 降序，与 `_applyDecisions` 一致）。
   - rollout 模式：对每个决策点 × 每个候选动作，同 seed 重放 + 强制首决策，记录终局名次。
   - 对照报告：每个决策点输出 policy 排序 vs rollout 排序、top-1 分歧、名次差，汇总分歧率。
   - 诊断模式：`--diag-repro`（同局连跑 3 次校验确定性）、`--diag-full`（全状态逐回合
     字段级 diff，定位首个分叉坐标——本次用它挖出卡表污染根因）。

**候选动作集**：收集时保留合法候选（买随从/买法术/升级/刷新/卖/饰品选择），按成本
过滤可用者。每次强制一个候选，其余候选不参与该次重放（单反事实）。

**验证标准**：
- 确定性检查：同 seed 纯重放（无强制）名次 == 收集局名次（逐位一致）。
- 强制候选在回合 T 前不改变任何行为（状态指纹一致断言）。
- 报告输出每个决策点的分歧明细（含 turn/tier/gold/候选表/名次表）。

# 增补（2026-09-08）：组合记忆 + 上限/破局推理层

> 触发：用户判定"算法缺乏有效记忆、无法关联机制/卡牌，复杂局面想不出快速提战力、够到上限的破局动作"。
> 本增补把该症状翻译成可实现的机制，挂在三层架构的层 2 之前作为 **决策前的组合推理**。

## 一、代码级实证（症状 → 结构性缺口）

| 用户症状 | 现有代码事实 | 缺口 |
|---|---|---|
| 缺记忆 | `StrategicMemory` 只记单卡观测集（ObservedCore/PairCardIds）+ 3 回合战力趋势；`_lastStrategyPlan` 仅在少数点被消费（首步贴合 3022/核心卡保护 2612/趋势 562） | 记忆是"卡集合+趋势"，**不是组合进度**——不知"在追体系 X、缺引擎 Y、对子进度 2/3、距启动差一步" |
| 无法关联 | 关联停在 classifier 角色（economy/amplifier）+ SynergyEngine 种族亲和 + CompGuideCatalog 选主线；C# 侧无 Ceiling/破局/组合状态概念（已检索确认） | 缺**"机制×卡×局势→破局窗口"组合算子**：无人计算"现有板面 + 本回合/下回合可达动作 → 哪条体系的战力/上限提升最大" |
| 想不到破局 | `GetBestAction` = 规则瀑布（R0~R238+，多处 early-return）；组合推理没有机会先于瀑布执行 | 瀑布内每条规则只看自己触发器；**无"本板面上限 vs 转型上限"对照 → 无破局判断依据** |

## 二、补法（决策前置的组合推理层）

全部用机制特征 + 版本化数据实现，不硬编码新赛季卡（遵守数据边界），产出先在 Shadow。

1. **组合状态模型（CompositionState）**：从 board/shop/hand/trinketOffer/hero/gold/turn 推断——
   每候选体系：引擎在场度、核心卡就绪、关键对子/三连进度、法术/经济生成器、饰品协同、距"启动回合"的缺口清单。
2. **上限估计（CeilingEstimator）**：数据驱动（comp 库/CompGuideCatalog/META_STRATEGY_LIBRARY 版本化）——
   每条体系给"成型终局模板 + 战力上限估计 + 关键缺口卡"。数值用模拟器同 seed rollout 标定，不用拍脑袋。
3. **破局搜索（BreakthroughSearch）**：决策时对 2~3 条候选体系做"缺口→本回合/近 2 回合可达动作"映射
   （买缺口引擎/攒对子等三连/升本开高星窗/用法术生成器触发引擎/饰品配合），输出带置信的
   "体系优先级 + 关键动作 + 破局窗口"; 置于规则瀑布之前，瀑布降级为硬约束 + 安全网。
4. **记忆升级（CompositionMemory）**：跨回合记录"本局追 X 体系、缺 Y、对子进度 Z"，决策不每回合从零推断；
   现有 StrategicMemory 扩展为结构化进度而非单卡集合。

## 三、验证（先证"缺口存在且可测"，再谈上线）

- **Ceiling-gap 度量（阶段 1 rollout 工具的扩展，证据优先）**：确定性模拟器里，取真实决策点，
  对照三条轨迹名次差——①当前策略自然轨迹 ②破局搜索推荐体系轨迹 ③该状态已知最优参考——
  "策略 vs 推荐"的名次差 = 破局能力缺口，逐决策点聚合成分歧清单（同 rollout-report 模式）。
- 无真实新赛季数据前：新层 Shadow + legacy 兜底；300 场景 + owner 门禁不破。
- 分层审计纪律（2026-09-07）：条件化（到某阶段才比该阶段）+ 逐状态反事实，不用朴素帧级配对下结论。
